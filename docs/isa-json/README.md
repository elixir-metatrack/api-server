# ISA-JSON export and import

Experimental. Metatrack exports a project (or a sample selection) as ISA-JSON that MARS can submit to
BioSamples and ENA, and imports ISA-JSON from other tools. Checking exports against repository checklists
(e.g. ENA) is a separate topic.

Everything for this topic is in this folder:

- `diagrams/`: SVGs with their PlantUML sources
- `example.json`: a synthetic export
- `scripts/seed-isa-demo.py`: demo projects and an export on the local API
- `scripts/validate-isa-json.py`: checks an export against the ISA and MARS schemas
- `scripts/mars-offline-check/`: runs an export through MARS without submitting

Commands below are run from the `api-server` root.

## Try it locally

```sh
make infra api          # from the workspace root
API_URL=http://localhost:1235/api python3 docs/isa-json/scripts/seed-isa-demo.py
```

The seed script creates `isa-json-demo` (two samples, all custom field types, one experiment, four pending
FASTQ records) and `isa-json-demo-subset`, and saves an export to `target/isa-demo.json`.

| Endpoint | Role |
| --- | --- |
| `GET /api/projects/{id}/exports/isa-json` – whole visible project | VIEWER |
| `POST /api/projects/{id}/exports/isa-json` with `{"sampleNames": [...]}` – selected samples | VIEWER |
| `POST /api/projects/{id}/imports/isa-json?commit=false\|true&study=<identifier>` | EDITOR (ADMIN for new custom fields) |

In the webapp: the table download menu has an ISA-JSON entry, the samples tab has **Import ISA-JSON**.

To check an export against the ISA and MARS schemas (pinned checkouts):

```sh
git clone https://github.com/ISA-tools/isa-specs.git /tmp/isa-specs
git -C /tmp/isa-specs checkout ed80675acb5ff98249e9821067eff83740d809d6
git clone https://github.com/elixir-europe/MARS.git /tmp/mars
git -C /tmp/mars checkout 8cc6fca592ff1695bd795144d7816bef984712df
uv run --with jsonschema==4.25.1 python docs/isa-json/scripts/validate-isa-json.py target/isa-demo.json \
  --isa-schema-dir /tmp/isa-specs/source/_static/isajson \
  --mars-schema /tmp/mars/schemas/isa_json.schema.json
```

To run an export through the MARS ENA adapter without submitting anything (needs Docker):

```sh
docs/isa-json/scripts/mars-offline-check/run.sh target/isa-demo.json
```

The script builds MARS (pinned commit) in Docker and prints the ENA study/experiment/run XML that MARS
would send to Webin. Samples without an `accession` get the placeholder `SAMEA0000000`, because the
BioSamples step is not run.

## Goals and principles

From the requirement: Metatrack must (1) generate ISA-JSON that downstream tools, specifically
**MARS**, can consume, (2) import ISA-JSON generated by third-party tools, and (3) cover
user-defined attributes.

1. **Shaped for MARS.** The export follows the structure the MARS adapters walk:
   source → sample → library → sequencing → data file (see [Why this shape](#why-this-shape)).
2. **Lossless round trip for Metatrack data.** Export → import into an empty project recreates the
   same samples, field values, custom fields, assays and file records. Where a repository convention
   and losslessness conflict, the Metatrack value is kept and only renamed.
3. **Nothing invented.** Values that Metatrack does not record are not generated, with two
   documented exceptions: the derived library (rule E5) and `DESIGN_DESCRIPTION` (rule E6).
4. **Import previews before writing.** Unsupported or ambiguous content is reported, never dropped silently.

## Export rules

**E1 · Investigation + one study ← project.** Title and description in both. A subproject is
exported as the visible subset of its parent's data; it does not become an additional study.
A sample selection (`POST …/exports/isa-json` with `{"sampleNames": […]}`) narrows the export to those samples,
their experiments and files; experiments without a selected sample are left out. Unknown names → 404.

**E2 · Identifiers.** `urn:metatrack:<instance>:<kind>:<id>` for every `@id`, e.g.
`urn:metatrack:metatrack.no:sample:<uuid>`. `<instance>` comes from the configuration property
`metatrack.isa.instance-id` (default: `local`). Investigation/study `identifier` =
`metatrack:<instance>:project:<id>`.

**E3 · Source ← one source per sample**, same name as the sample, carrying `organism` and `tax_id`.
A study process `sample collection` has the source as input and the sample as output; the sample
also has `derivesFrom` → source.

**E4 · Sample ← sample.** Characteristics follow the [field register](#sample-field-register).
Every value is an OntologyAnnotation object (`{"annotationValue": "…"}`), also numbers, booleans and dates
(as strings), because MARS models `value` as an object. Organisms get `termSource: NCBITaxon` and
`termAccession: http://purl.obolibrary.org/obo/NCBITaxon_<taxId>`, plus the scientific name from TaxHub.
If TaxHub is unavailable, `annotationValue` is the numeric ID and the export notes this in a comment.
Empty fields are omitted.

**E5 · Library ← derived, one per sample × assay that has files.** `otherMaterials[]` with
`type: "Extract Name"` (ISA has no library type), name `<sample> / <assay>`, `derivesFrom` → sample.
Justification: sequence files imply that a library was prepared. Extraction and pooling are not modelled.

**E6 · Assay ← assay.** One ISA assay per Metatrack assay, with two protocols and, per sample with
files, two processes:
- `library construction`: protocol name = `libraryName`; parameters `LIBRARY_NAME` (= sample name),
  `LIBRARY_CONSTRUCTION_PROTOCOL` (= `libraryName`), `LIBRARY_SOURCE`, `LIBRARY_SELECTION`,
  `LIBRARY_STRATEGY`, `LIBRARY_LAYOUT`, `NOMINAL_LENGTH` (= `insertSize`), `DESIGN_DESCRIPTION`
  (generated: "`<strategy>` of `<source>` material, `<selection>` selection, `<layout>` layout, `<libraryName>`",
  marked with the comment `metatrack:generated=DESIGN_DESCRIPTION`).
- `nucleic acid sequencing`: parameters `PLATFORM`, `INSTRUMENT_MODEL`; `performer` = `sequencingLaboratory`.
- Processes are linked with `previousProcess`/`nextProcess`.
- Assay fields: `measurementType` / `technologyType` from `libraryStrategy` (table below),
  `technologyPlatform` = "`<platform>` `<instrument>`". Comments: `metatrack:assayName`,
  `metatrack:studyAccession`, `metatrack:experimentAccession`, `metatrack:runAccession`, `STUDY_TYPE` (table below).

| `libraryStrategy` | `measurementType` | `technologyType` | `STUDY_TYPE` |
| --- | --- | --- | --- |
| WGS, WGA, WCS | genome sequencing | nucleotide sequencing | Whole Genome Sequencing |
| AMPLICON | amplicon sequencing | nucleotide sequencing | Other |
| RNA-Seq | transcription profiling | nucleotide sequencing | Transcriptome Analysis |
| anything else / empty | – | nucleotide sequencing | Other |

**E7 · Files ← files of the assay.** `dataFiles[]`, each the output of exactly one sequencing process.
`type: Raw Data File` for FASTQ/BAM/CRAM; comments `file type` (by extension), `file checksum` (md5),
`checksum_method: MD5`, `metatrack:unencryptedMd5`, `metatrack:readRole`, `metatrack:uploadStatus`.
PENDING files are exported (status is visible in the comment).

**E8 · Abort instead of guessing.** The export fails with a list of the affected records if
- a file belongs to an assay whose sample is not an assay member (known AssayService case),
- the files of one sample × assay are not one valid run: allowed are one `SINGLE` file, one
  `FORWARD` + one `REVERSE`, or exactly one file without a role (multiple runs per sample × assay are
  not supported for now),
- `libraryLayout` contradicts the read roles (PAIRED with a single file, SINGLE with a pair).

**Not exported:** `hostSubjectId` (patient reference), audit timestamps, members, storage keys/paths,
archived custom fields. Allowed-value lists of vocabularies are not exported (values are).

## Import rules

**Endpoints.** Export: `GET /api/projects/{id}/exports/isa-json` (VIEWER). Import:
`POST /api/projects/{id}/imports/isa-json?commit=false|true&study=<identifier>` with the ISA-JSON document as
the request body (EDITOR). In the webapp: download menu → **ISA-JSON (.json)**; samples tab → **Import ISA-JSON**.

**I1 · Input and target.** Accepts an Investigation document or the MARS wrapper `{"investigation": …}`.
The data is imported into an **existing** project (like the CSV imports). Exactly one study is
imported; if the document has several, the caller chooses it by `identifier` (otherwise rejected).
Required role: EDITOR; ADMIN if new custom fields have to be created (same as creating fields manually).

**I2 · Two steps.** `preview` returns what would be created (samples, fields, assays, files),
what is ignored and all conflicts, without writing. `commit` performs the same import in one
transaction; it fails completely if any blocking error exists.

**I3 · Samples.** Every `Study.materials.samples[]` becomes a Metatrack sample (`name` required).
Characteristics of its sources (via `derivesFrom` or any study process from source to sample) are merged in;
the sample's own value wins. Matching per characteristic:
1. comment `metatrack:fieldKey` → existing custom field with that key, otherwise a new one with that key and type;
2. name in the field register → built-in field;
3. otherwise → custom field: reuse a field with the same label, else create one (key = label in
   snake_case, type TEXT). Numbers stay text unless all values of the category are numeric (then NUMBER).

Value conversion: `annotationValue` of objects, plain strings and numbers are accepted. `organism`/`host`
→ tax ID from the `termAccession` or value in the notations `287`, `NCBI:txid287`, `NCBITaxon_287`;
a name without any ID is rejected (TaxHub resolves IDs to names, not names to IDs).
Custom fields declared by a Metatrack export (`metatrack:fieldKey`) are created even if no sample has a
value, including their tooltip. A unit, if present, is appended to the text value ("25 years").
Dates must be ISO (`YYYY-MM-DD`); truncated dates (`2021-06`) are rejected for `collectionDate`
because Metatrack stores full dates only. Values are checked against the project's sample vocabularies,
as in the CSV import.

**I4 · Conflicts.** A sample name that already exists in the project, a duplicate name in the file,
or an invalid value → row-level error (same messages as the CSV import), blocking the commit.
Existing samples are never updated by an ISA import.

**I5 · Assays.** Every ISA assay becomes a Metatrack assay (name: comment `metatrack:assayName`,
else the assay `filename` without `a_` prefix and extension; must be unique in the project).
Assay fields are read from process parameter values by name (case-insensitive, also with spaces):
`LIBRARY_SOURCE`, `LIBRARY_SELECTION`, `LIBRARY_STRATEGY`, `LIBRARY_LAYOUT`, `NOMINAL_LENGTH` → `insertSize`,
`PLATFORM`, `INSTRUMENT_MODEL` (fallback `technologyPlatform`), `LIBRARY_CONSTRUCTION_PROTOCOL`
(fallback protocol name) → `libraryName`, process `performer` → `sequencingLaboratory`, comment
`metatrack:studyAccession` → `studyAccession`. If these values differ between the samples of one assay
→ blocking error, because a Metatrack assay holds one value per field. `LIBRARY_NAME` and
`DESIGN_DESCRIPTION` have no Metatrack field and are reported as ignored.

**I6 · Membership and files.** Each data file is traced back: file ← process output ← library/extract
(`derivesFrom` or process input, repeated) ← sample. The sample becomes an assay member; the file
becomes a PENDING file record of that sample × assay with name, md5 (`file checksum`), unencrypted md5
and read role (comment `metatrack:readRole`; else `_R1`/`_1` → FORWARD, `_R2`/`_2` → REVERSE; else SINGLE
for layout SINGLE; else empty). Files that lead to no sample or to several samples (e.g. pooled analysis results), and files without
md5 checksum, are **not imported and listed** in the preview; the samples and experiments are still imported.
Samples in `assay.materials.samples` without files still become members. File contents are not
transferred; uploading works as for files imported via the experiment CSV.

**Preview response:** study, available studies (to choose from), samples, new custom fields with type,
experiments with sample/file counts, ignored content, errors. A commit with errors returns HTTP 422 and writes nothing.

**I7 · Reported as ignored (not blocking):** additional studies, factors and factor values,
publications, people/contacts, ontology source references, protocol descriptions, ontology accessions
other than organisms, extract and labeled-extract details, `LIBRARY_NAME`, `DESIGN_DESCRIPTION`,
processes not on a file lineage, derived data files.

## Why this shape

| Finding | Evidence |
| --- | --- |
| Starting from each data file, the MARS ENA adapter looks for the producing process and its input `otherMaterial` (library). Without it, no ENA experiment is created. | `WebinExperimentXmlCreator.mapExperimentForDataFile` (MARS `8cc6fca`) |
| The MARS BioSamples adapter registers sources and samples ("derived from") and reads `value.annotationValue`. In the MARS model `Characteristic.value` and `ParameterValue.value` are objects; plain string values do not fit. | `BioSamplesSubmitter`; `mars-repository-lib` v0.0.2 `models/isa/Value.java` |
| BioSamples/ENA expect names like `collection date`, `geographic location (country and/or sea)`. | MARS constants; ENA checklists via `ebi.ac.uk/ena/browser/api/xml/ERC0000xx` |
| The ENA adapter creates one ENA study per ISA assay and requires `STUDY_TYPE`, `DESIGN_DESCRIPTION`, `PLATFORM`, `INSTRUMENT_MODEL`. | `WebinStudyXmlCreator`, `WebinExperimentXmlCreator` |
| The Metatrack templates already follow the ENA checklists; the "Library Name" example is a kit (`Illumina DNA prep`). | `templates/samples/*.csv`, `templates/experiments/experiment_PE.csv` |
| The experiment import enforces one value per assay field (`hasMetadataConflict`): an assay is one homogeneous sequencing setup. | `CSVExperimentImportService` |

## Decisions and assumptions

| Topic | Decision | Revisit when |
| --- | --- | --- |
| Source | One source per sample. MARS would register two BioSamples per isolate; checked in the MARS step. | MARS test shows a problem |
| Patient reference | `hostSubjectId` is not exported; import accepts it. | Data protection decision |
| Runs | One run per sample × assay; otherwise the export aborts. | Real data with several lanes/runs |
| `libraryName` | Treated as kit/protocol (template example). | Users name individual libraries |
| `DESIGN_DESCRIPTION` | Generated in the export, marked; not stored on import. | A real design field is needed |
| `isolate`, `county`/`commune`, `hostAge` | Exported as stored; no fallback, merging or unit invented. | Checklist validation issue |
| Instance ID | Config property, default `local`. | First exchange between installations |
| Checklist conformance | Not checked here. | Separate issue |

## Verification

- API tests (`./mvnw test`, Java 25+) include `IsaJsonRoundTripTest` (PostgreSQL:
  export → preview → import into an empty project → export, identical content; conflicts write nothing;
  new fields need ADMIN) and register coverage (`everySampleFieldIsInTheRegister…`).
- Local round trips on the running API: demo project (2 samples, 4 custom field types, 1 experiment,
  4 files) and the 79-sample project: re-export identical in content.
- Third-party files (preview): MARS `biosamples-input-isa.json` and `ISA-BH2024-ALL` and the ARC example
  (`TalinumFacultativeCAM`, after choosing one of two studies) preview without blocking errors; unsupported
  parts are listed as not imported.


- [example.json](example.json) (synthetic, values from the templates) passes
  the ISA schema, the MARS schema, internal references, unique definitions and "every file has a
  producing process" (`scripts/validate-isa-json.py`).
- **MARS ENA adapter, offline (2026-10-29, repeated 2026-11-06 with `scripts/mars-offline-check`):** MARS `8cc6fca`
  + `mars-repository-lib` v0.0.2 built in Docker; the script calls the adapter's study/experiment/run XML creators
  exactly as `performSubmissionToEna` does, but stops before the Webin submission. With an `accession` on each
  sample, every experiment references its own sample.
  | Input | Result |
  | --- | --- |
  | MARS's own fixture `biosamples-input-isa.json` (control) | OK, 1 experiment, 1 run |
  | first prototype export (plain string values) | fails: MARS cannot read plain string values (`Value` must be an object) |
  | export of the demo project (2 samples, paired FASTQ) | fails: `Missing required ENA experiment metadata PLATFORM` (the demo assay has no sequencing platform) |

  | export of the 79-sample project (no experiments) | OK, nothing to submit to ENA (BioSamples only) |
  | export after adding the platform to the demo seed (`scripts/seed-isa-demo.py`) | OK: 2 experiments, 2 runs, no manual changes |
- **Not yet run:** the MARS BioSamples adapter (it submits directly to BioSamples) and a submission to the ENA test server (needs a Webin account).
